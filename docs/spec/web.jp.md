# Web シミュレーター

[English](web.md)

Web シミュレーターは、コアをブラウザで Wasm として動かす。ページは `web/` にある TypeScript で、Wasm モジュールはクレート `mblint-wasm` である。

## Wasm のインターフェース

モジュールは次の関数を公開する。どれも、読んでよいファイルを、パスからファイルの内容への対応を持つオブジェクトとして受け取る。パスは[データスキーマ](schema.jp.md)のパスの規則に従う。

| 関数 | 引数 | 戻り値 |
| --- | --- | --- |
| `check(files, rig)` | `files` と、rig ファイルのパス `rig` | [コマンドライン](cli.jp.md)にある `mblint check --json` のレポート |
| `lint(files, board)` | `files` と、ボードファイルのパス `board` | `mblint lint --json` のレポート |
| `catalog(files)` | `files` | 各ファイルが何であるか。[カタログ](#カタログ)のとおり |
| `layout(files, rig)` | `files` と、rig ファイルのパス `rig` | ページが描く形での rig のボード。[レイアウト](#レイアウト)のとおり |

ファイルは、CLI がデータルートの下から読むのと同じく、rig か呼び出しが名指すパスでだけ読む。`files` に無いパスは読めない。

ファイルを読み込めないときは、ファイル名とその理由を述べるメッセージ、つまり CLI が標準エラーで `mblint: ` に続けて出すメッセージを持つ `Error` を投げる。レポートは返さない。

## カタログ

`catalog(files)` は、`files` のすべてのパスをキーとし、そこにあるファイルが何であるかを値とするオブジェクトを返す。ファイルの種類は、パスではなく中身で決める。ボードとして解釈できればボード、デバイスとして解釈できればデバイス、rig として解釈できれば rig である。三つの必須フィールドは重ならないので、当てはまるのは多くとも一つである。

```json
{
  "boards/asus/proart_x870e_creator_wifi.toml": {
    "kind": "board", "vendor": "ASUS", "model": "ProArt X870E-CREATOR WIFI"
  },
  "devices/rtx_a400.toml": {
    "kind": "device", "name": "NVIDIA RTX A400 4GB", "type": "card",
    "interface": { "protocol": "pcie", "generation": 4, "lanes": 8 },
    "socket_category": "pcie_slot"
  },
  "rigs/workstation.toml": {
    "kind": "rig", "name": "workstation", "board": "boards/asus/proart_x870e_creator_wifi.toml",
    "bindings": { "PCIEX16(G5)_1": "devices/rtx_a400.toml" }
  },
  "notes.toml": { "kind": "invalid", "message": "not a board: …; not a device: …; not a rig: …" }
}
```

| `kind` | フィールド |
| --- | --- |
| `board` | ボードの `vendor` と `model` |
| `device` | デバイスの `name` と `type`。デバイス自身のリンク `interface`（アダプタとディスプレイでは `null`）。装着するボードのソケットのカテゴリ `socket_category` |
| `rig` | rig の `name`、そのボードのパス `board`、各ソケットのパスに装着するデバイスのパス `bindings` |
| `invalid` | ボードでない理由、デバイスでない理由、rig でない理由を述べる `message` |

`socket_category` は、カードなら `pcie_slot`、M.2 モジュールなら `m2_slot`、ディスプレイなら `usb_c`、アダプタなら上流のコネクタに応じて `usb_c` か `usb_a` である。

## レイアウト

`layout(files, rig)` は、rig のボードのすべてのノードを、ノード ID をキーとして返す。各ノードには、rig が装着するデバイスによってそのノードがどうなるかを付ける。パスがエラーを報告するかどうかにかかわらず rig だけから求めるので、エラーのある rig も描ける。

```json
{
  "root_cpu": { "kind": "root", "parent": null, "generation": 5, "supplied": 20, "demanded": 16 },
  "mux_cpu_x16": { "kind": "mux", "parent": "root_cpu", "mode": 1 },
  "PCIEX16(G5)_1": {
    "kind": "socket", "parent": "mux_cpu_x16", "category": "pcie_slot", "slot_index": 2,
    "device": "devices/rtx_a400.toml", "disabled": false,
    "offers": { "generation": 5, "lanes": 8 }, "needs": { "generation": 4, "lanes": 8 }
  }
}
```

| `kind` | `parent` 以外のフィールド |
| --- | --- |
| `root` | `generation`。供給するレーン数 `supplied`。子が要求するレーン数を Pass 2 と同じ数え方で数えた `demanded` |
| `mux` | 選ばれたモードの、宣言順で 0 から数えた位置 `mode`。どのモードも成り立たないときは `null` |
| `bridge` | 親に要求する上流のレーン数 `lanes` |
| `controller` | なし |
| `socket` | `category`。`slot_index`（PCIe スロット以外のソケットでは `null`）。rig がそこに装着するデバイスファイルのパス `device`（無ければ `null`）。Mux の選ばれたモードがそれを無効にするかどうか `disabled`。Pass 4 がリンクを評価するときと同じく求めた、ソケットが出せる世代とレーン数 `offers`（レーン数を述べないソケットでは `null`）。装着したデバイスの PCIe リンクの世代とレーン数 `needs`（ソケットが空か、デバイスが PCIe を使わないときは `null`） |

`parent` はノードの親の ID で、ルートとコントローラでは `null` である。アダプタの中のソケットはレイアウトに含めない。

## ページ

ページは、ボードの上で rig を組み、ボードがそれをどう扱うかを示す。

### ファイル

ページは、`data/` の下のすべてのファイルを、`data/` からのパスをキーとする `files` として持つ。利用者が読み込んだファイルは `local/<ファイル名>` に加え、同じ名前の読み込み済みのファイルがあれば置き換える。読み込んだファイルはブラウザの中にだけ置き、どこにも送らない。

一つの操作で TOML ファイルを読み込む。ファイルはディスクから選ぶか、ページのどこかにドロップする。各ファイルが何であるかは `catalog` が決める。

| 種類 | 結果 |
| --- | --- |
| ボード | ボードに加え、そのボードを選ぶ |
| デバイス | パーツに加える |
| rig | そのボードを選び、その割り当てを装着する。名指すパスが `files` に無ければ、一緒に読み込んだファイルのうち、名前がそのパスの最後の部分と同じものを使う。どちらにも無いパスは、名前を挙げて知らせる |
| 読めないもの | ファイル名とともにそのメッセージを知らせる |

### rig

ページは、組んでいる rig を、選んだボードの上の rig ファイルとして `files` の `local/rig.toml` に置き、変わるたびに `check` と `layout` で評価する。別のボードを選ぶと、rig は空になる。

パーツは `files` の中のデバイスで、それぞれ名前とインターフェースを示す。パーツは、選んでからソケットを選ぶか、ソケットへドラッグして置く。パーツを受けるのは、カテゴリがそのパーツの `socket_category` と同じソケットだけで、パーツを選んでいる間はそのソケットに印を付ける。デバイスのあるソケットにパーツを置くと、そのデバイスと置き換える。デバイスは、ソケットにある操作で外す。

### トーナメント表

各ルートをトーナメント表として描く。ソケットを左の葉に置き、Mux とブリッジを経て右のルートへまとめる。ルートは、世代の高い順、次に供給するレーン数の多い順、次に ID の順に描く。各子からその兄弟の合流点へ線を引き、合流点から親へも線を引く。線は一つの太さで、中心どうしで交わるので、合流点を通る線はまっすぐ続く。Mux は、選ばれたモードの 1 から数えた位置か、どのモードも成り立たないことを示す。ブリッジは要求するレーン数を示す。親が `unknown` のソケットは、ルートとは別にまとめて描く。コントローラは描かない。

ソケットは、ID、装着したデバイス、Gbps の一つの目盛りに乗る 2 本のバーを示す。上がデバイスの求めるもの、下がソケットの出せるものである。各バーはレーン 1 本を 1 ブロックとし、ブロックの幅をその世代のレーン 1 本の速度にする。これで、2 本のバーはレーン数と世代の両方を比べる。目盛りはボードごとに決め、どのボードでも、そのボードでいちばん長いソケットのバーを一定の幅で描く。上のバーのうち下を超えた部分は不足として印を付け、下のバーのうち上を超えた部分は薄く描く。空のソケットは出せるものだけを示し、何も出さないソケットはバーを示さない。Mux が無効にしたソケットは、取り消し線を付けて描く。

ルートは、レーン数で数える 2 本のバーを示す。各ブロックがレーン 1 本である。上が子の要求するレーン数、下が供給するレーン数である。そのボードでいちばん長いルートのバーも、同じ一定の幅で描く。供給を超えた要求には、超過として印を付ける。

### レポート

レポートの状態、各診断の重大度・メッセージ・コード、評価したデバイスそれぞれのリンクを示す。

### 見た目

ボードとパーツは左のサイドバーに並べ、レポートは右のサイドバーに置き、トーナメント表はその間に置く。ヘッダーの色がウィンドウを囲む枠になり、二つのサイドバーとトーナメント表は、それぞれその枠にはめ込んだ角の丸みの小さいくぼみの中にある。サイドバーの内側の縁をドラッグするか矢印キーで動かすと、サイドバーの幅が 180 から 480 ピクセルの間で変わり、その幅をブラウザに記憶する。縁をダブルクリックすると、初めの幅に戻る。各サイドバーは、下端の操作で細いアイコンの列に畳み、その列から開き直す。それぞれが開いているかどうかをブラウザに記憶する。狭い画面では、この三つをこの順に縦に重ね、畳んだサイドバーはアイコンを横一列に並べる。

ヘッダーの操作はアイコンで示し、それぞれの名前をツールチップに出す。操作は、ファイルの読み込み、rig を空にすること、ライトとダークのテーマの切り替え、設定を開く歯車である。

設定では、テーマ（システムのライトかダーク、ライト、ダークのいずれか）と、ヘッダーの操作の名前をアイコンの横に出すかどうかを選ぶ。どちらもブラウザに記憶する。テーマを切り替えるか選ぶと、新しいテーマがその操作から広がる円の中に現れる。システムが動きを減らすよう求めているときは、すぐに切り替える。ページは最初の描画からそのテーマで描き、モジュールを読み込む間もサイドバーとトーナメント表の位置を保つ。これで、ページを読み込むときに別のテーマが一瞬見えることも、配置が組み変わることもない。ページは横にスクロールしない。スクロールが要る部分は、テーマの色の細いスクロールバーを持ち、ポインタがその部分にある間だけそれを見せる。

## ビルド

Wasm モジュールは、`mblint-wasm` を `wasm32-unknown-unknown` 向けにビルドし、`wasm-bindgen` コマンドラインで TypeScript の宣言付きの ES モジュールにしたものである。コマンドラインは、`Cargo.lock` にある `wasm-bindgen` クレートと同じ版でなければならない。

ページは、`web/dist` の静的アセットを配る Cloudflare Worker として mblint.shortarrow.jp に公開する。設定は `web/wrangler.jsonc` にある。Cloudflare Workers Builds は `main` を公開し、ほかのブランチを preview としてビルドする。そのとき `web/scripts/cloudflare-build.sh` を実行し、ページをビルドする前に Rust と `wasm-bindgen` コマンドラインを入れる。

レポート、カタログ、レイアウトの TypeScript の型は、コアの Rust の型から ts-rs で、型ごとに一つのファイルとして `web/src/report/` に生成する。`cargo test -p mblint-core --features ts` がこれを書き出し、そこにコミットされたファイルが書き出したものと異なるとき、CI は失敗する。各パスの診断の型は、パスの名前を冠して `PhysicalDiagnostic`、`LanesDiagnostic`、`TunnelsDiagnostic`、`ThroughputDiagnostic` と呼ぶ。
