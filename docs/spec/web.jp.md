# Web シミュレーター

[English](web.md)

Web シミュレーターは、コアをブラウザで Wasm として動かす。ページは `web/` にある TypeScript で、Wasm モジュールはクレート `mblint-wasm` である。

## Wasm のインターフェース

モジュールは次の関数を公開する。`rebind` 以外はどれも、読んでよいファイルを、パスからファイルの内容への対応を持つオブジェクトとして受け取る。パスは[データスキーマ](schema.jp.md)のパスの規則に従う。

| 関数 | 引数 | 戻り値 |
| --- | --- | --- |
| `check(files, rig)` | `files` と、rig ファイルのパス `rig` | [コマンドライン](cli.jp.md)にある `mblint check --json` のレポート |
| `lint(files, board)` | `files` と、ボードファイルのパス `board` | `mblint lint --json` のレポート |
| `catalog(files)` | `files` | 各ファイルが何であるか。[カタログ](#カタログ)のとおり |
| `layout(files, rig)` | `files` と、rig ファイルのパス `rig` | ページが描く形での rig のボード。[レイアウト](#レイアウト)のとおり |
| `rebind(text, board, bindings)` | rig ファイルの `text`、パス `board`、各ソケットのパスからデバイスのパスへの対応を持つオブジェクト `bindings` | rig の board と bindings を `board` と `bindings` に置き換えた `text`。[割り当ての書き換え](#割り当ての書き換え)のとおり |

ファイルは、CLI がデータルートの下から読むのと同じく、rig か呼び出しが名指すパスでだけ読む。`files` に無いパスは読めない。

ファイルを読み込めないときは、ファイル名とその理由を述べるメッセージ、つまり CLI が標準エラーで `mblint: ` に続けて出すメッセージを持つ `Error` を投げる。レポートは返さない。

### 割り当ての書き換え

`rebind` は、違う値だけを変え、`text` のほかの部分は、コメント、順序、書き方も含めてそのまま残す。ソケットが `bindings` にある割り当ては、その位置のまま新しいパスになる。ソケットが `bindings` に無い割り当ては、その行の末尾のコメントとともに消す。その上の行のコメントは消さず、次の割り当ての上か、割り当ての末尾に残す。rig に無かったソケットは、最後の割り当ての後に加える。割り当ては、表かインラインの表か、`text` の書き方を保つ。割り当てを持たない rig には、末尾に `[bindings]` の表を加える。`text` が rig でないときは、ほかの関数と同じく例外を投げる。

## カタログ

`catalog(files)` は、`files` のすべてのパスをキーとし、そこにあるファイルが何であるかを値とするオブジェクトを返す。ファイルの種類は、パスではなく中身で決める。ボードとして解釈できればボード、デバイスとして解釈できればデバイス、rig として解釈できれば rig である。三つの必須フィールドは重ならないので、当てはまるのは多くとも一つである。

```json
{
  "boards/asus/proart_x870e_creator_wifi.toml": {
    "kind": "board", "vendor": "ASUS", "model": "ProArt X870E-CREATOR WIFI"
  },
  "devices/rtx_a400.toml": {
    "kind": "device", "name": "NVIDIA RTX A400 4GB", "type": "card",
    "interface": { "protocol": "pcie", "generation": 4, "lanes": 8 },
    "socket_category": "pcie_slot"
  },
  "rigs/workstation.toml": {
    "kind": "rig", "name": "workstation", "board": "boards/asus/proart_x870e_creator_wifi.toml",
    "bindings": { "PCIEX16(G5)_1": "devices/rtx_a400.toml" }
  },
  "notes.toml": { "kind": "invalid", "message": "not a board: …; not a device: …; not a rig: …" }
}
```

| `kind` | フィールド |
| --- | --- |
| `board` | ボードの `vendor` と `model` |
| `device` | デバイスの `name` と `type`。デバイス自身のリンク `interface`（アダプタとディスプレイでは `null`）。装着するボードのソケットのカテゴリ `socket_category` |
| `rig` | rig の `name`、そのボードのパス `board`、各ソケットのパスに装着するデバイスのパス `bindings` |
| `invalid` | ボードでない理由、デバイスでない理由、rig でない理由を述べる `message` |

`socket_category` は、カードなら `pcie_slot`、M.2 モジュールなら `m2_slot`、ディスプレイなら `usb_c`、アダプタなら上流のコネクタに応じて `usb_c` か `usb_a` である。

## レイアウト

`layout(files, rig)` は、rig のボードのすべてのノードを、ノード ID をキーとして返す。各ノードには、rig が装着するデバイスによってそのノードがどうなるかを付ける。パスがエラーを報告するかどうかにかかわらず rig だけから求めるので、エラーのある rig も描ける。

```json
{
  "root_cpu": { "kind": "root", "parent": null, "generation": 5, "supplied": 20, "demanded": 16 },
  "mux_cpu_x16": { "kind": "mux", "parent": "root_cpu", "mode": 1 },
  "PCIEX16(G5)_1": {
    "kind": "socket", "parent": "mux_cpu_x16", "category": "pcie_slot", "slot_index": 2,
    "device": "devices/rtx_a400.toml", "disabled": false,
    "offers": { "generation": 5, "lanes": 8 }, "needs": { "generation": 4, "lanes": 8 }
  }
}
```

| `kind` | `parent` 以外のフィールド |
| --- | --- |
| `root` | `generation`。供給するレーン数 `supplied`。子が要求するレーン数を Pass 2 と同じ数え方で数えた `demanded` |
| `mux` | 選ばれたモードの、宣言順で 0 から数えた位置 `mode`。どのモードも成り立たないときは `null` |
| `bridge` | 親に要求する上流のレーン数 `lanes` |
| `controller` | なし |
| `socket` | `category`。`slot_index`（PCIe スロット以外のソケットでは `null`）。rig がそこに装着するデバイスファイルのパス `device`（無ければ `null`）。Mux の選ばれたモードがそれを無効にするかどうか `disabled`。Pass 4 がリンクを評価するときと同じく求めた、ソケットが出せる世代とレーン数 `offers`（レーン数を述べないソケットでは `null`）。装着したデバイスの PCIe リンクの世代とレーン数 `needs`（ソケットが空か、デバイスが PCIe を使わないときは `null`） |

`parent` はノードの親の ID で、ルートとコントローラでは `null` である。アダプタの中のソケットはレイアウトに含めない。

## ページ

ページは、ボードの上で rig を組み、ボードがそれをどう扱うかを示す。

### ファイル

ページは、`data/` の下のすべてのファイルを、`data/` からのパスをキーとする `files` として持つ。利用者が読み込んだファイルは `local/<ファイル名>` に加え、同じ名前の読み込み済みのファイルがあれば置き換える。名前に `/` か `\` を含むファイルと、名前が `.` か `..` のファイルは加えず、そのことをページに示す。読み込んだファイルはブラウザの中にだけ置き、どこにも送らない。ファイルの文字列は、同梱のものも、読み込んだものも、編集したものも、文字列としてだけページに出し、HTML として解釈しない。

一つの操作で TOML ファイルを読み込む。ファイルはディスクから選ぶか、ページのどこかにドロップする。各ファイルが何であるかは `catalog` が決める。

| 種類 | 結果 |
| --- | --- |
| ボード | ボードに加え、そのボードを選ぶ |
| デバイス | パーツに加える |
| rig | rig の一覧に加え、適用する |
| 読めないもの | ファイル名とともにそのメッセージを知らせる |

別の操作で、利用者が示すアドレスから、公開されている GitHub のリポジトリにあるデータルートを読み込む。アドレスは、既定のブランチのルートを読む `https://github.com/<owner>/<repo>` か、ブランチ、タグ、コミットのどれか `<ref>` におけるフォルダー `<path>` を読む `https://github.com/<owner>/<repo>/tree/<ref>/<path>` で、`<ref>` は `/` を含まない。そのフォルダーとその下にある、名前が `.toml` で終わるすべてのファイルを、`github/<owner>/<repo>/` にそのフォルダーからのパスを続けたパスに加え、そのリポジトリから前に読み込んだファイルと置き換える。リポジトリの rig が名指すパスは、まずそのリポジトリのファイルから読む。これで、一つのリポジトリにボード、デバイス、rig をいくつでも置け、別のフォルダーに同じ名前のファイルを置ける。ボードとデバイスはそれぞれの一覧に加え、rig は rig の一覧に加えるが、リポジトリにある rig がちょうど一つのときを除いて適用しない。1 MiB より長いファイルと、パスに `\`、`:`、制御文字のどれかを含むファイルは加えず、ページはその名前を示す。アドレスが公開されたリポジトリを指さないとき、フォルダーに TOML ファイルが無いか 200 より多いとき、ページが問い合わせすぎて GitHub が断ったときは、ページはそのことを示し、何も加えない。ページは GitHub にサインインせずに問い合わせ、アドレスもファイルも記憶しない。

### rig

ページは、組んでいる rig を、選んだボードの上の rig ファイルとして `files` の `local/rig.toml` に置き、変わるたびに `check` と `layout` で評価する。別のボードを選ぶと、rig は空になる。

パーツは `files` の中のデバイスで、それぞれ名前とインターフェースを示す。パーツは、選んでからソケットを選ぶか、ソケットへドラッグして置く。パーツを受けるのは、カテゴリがそのパーツの `socket_category` と同じソケットだけで、パーツを選んでいる間はそのソケットに印を付ける。それ以外のものをソケットへドロップしても、何も起きない。デバイスのあるソケットにパーツを置くと、そのデバイスと置き換える。デバイスは、ソケットにある操作で外す。

rig の一覧は `files` の中の rig ファイルで、それぞれ名前を示す。rig は、読み込んだときか、一覧から選んだときに適用する。適用すると、そのボードを選び、その割り当てを装着する。名指すパスが `files` に無ければ、いつ読み込んだかに関わらず、名前がそのパスの最後の部分と同じ読み込み済みのファイルを使う。どちらにも無いパスは、名前を挙げて知らせる。組んでいる rig が一覧の rig と同じボードと割り当てを持つ間、一覧のその rig に印を付ける。

組んでいる rig は、展開するとデータルートになる zip アーカイブとして書き出す。中身は、`rigs/<名前>.toml` に置く rig と、その rig が名指す各ファイルである。各ファイルは `files` の中のパスに置くが、読み込んだボードは `boards/<ファイル名>` に、読み込んだデバイスは `devices/<ファイル名>` に置き、書き出す rig はそのパスで名指す。rig の名前は印の付いた rig の名前で、印の付いた rig が無ければ `rig` とし、アーカイブの名前にも使う。ファイルは圧縮せずに格納する。

### エディタ

一覧の各ボード、各パーツ、各 rig にある操作で、そのファイルをトーナメント表の横のエディタに、文字列として開く。編集するたびに、`files` の中のそのパスの文字列を置き換え、ほかの変更と同じように評価する。1 MiB より長い文字列と、`catalog` が読めない文字列は取り込まない。その理由を、原因の行があればその行とともに示し、トーナメント表とレポートは最後に示したものを保つ。編集したファイルは、そのファイルのダウンロードとして、または書き出すアーカイブに rig とともに入れて保存する。保存しない編集は、ページを開いている間だけ残る。

エディタは、文字列を TOML として色分けする。打っているキーは、ボード、デバイス、rig がその場所に持てるキーで補完を勧め、`=` の後の値は、そのフィールドの取りうる値が列挙されているとき、ソケットのカテゴリのように、その値で補完を勧める。文字列を取り込まないときは、問題の行に印を付ける。

rig をエディタで開いている間は、その rig が組み立て中の rig になる。開いたとき、そしてその rig への編集を取り込むたびに、その rig を適用する。パーツを置く、外す、rig を空にする、ボードを選び直す、という組み立て中の rig への変更は、`rebind` でその rig の文字列に書き込み、エディタに示す。変更が触れない割り当ては、読み込まれていないファイルのものも含めて、rig が名指すパスのまま残す。新しいパスは `files` の中のパスで書き、rig とそのファイルが同じリポジトリから来たときは、接頭辞 `github/<owner>/<repo>/` を除いて書く。

### 新しいファイル

ボードの一覧の見出しの横にある操作でボードを作り、パーツの一覧の見出しの横にある操作で、カード、M.2 モジュール、アダプター、ディスプレイのどれかをメニューから選んで作る。新しいファイルは、`catalog` が読める、その種類で最小のファイルで、必須のフィールドにはそれぞれ例の値が入る。ボードには一つのルートとその下の一つの PCIe スロットがあり、アダプターには一つの下流のソケットがある。ファイルは `local/new-<種類>.toml` に加える。`<種類>` は `board`、`card`、`m2-module`、`adapter`、`display` のどれかである。そのパスがすでに `files` にあるときは、`local/new-<種類>-<n>.toml` に加える。`<n>` は、2 から数えて `files` にまだない最小の数で、新しいファイルがほかのファイルを置き換えることはない。加えたファイルは、その種類のファイルを読み込んだときと同じ働きをし、エディタで開く。例の値は未規定とする。

リグの一覧の見出しの横にある操作は、ボードを選んでいる間だけ使え、リグを作る。作るのは組み立て中のリグで、そのボードとその割り当てを持つ。ファイルは `local/new-rig.toml` に加え、そのパスがすでにあるときはほかの種類の新しいファイルと同じく `local/new-rig-<n>.toml` に加える。リグの名前は、ファイルの名前から `.toml` を除いたものである。加えたリグは適用し、組み立て中のリグはそのままで、新しいリグに印が付く。そしてエディタで開く。

### トーナメント表

各ルートをトーナメント表として描く。ソケットを左の葉に置き、Mux とブリッジを経て右のルートへまとめる。ルートは、世代の高い順、次に供給するレーン数の多い順、次に ID の順に描く。各子からその兄弟の合流点へ線を引き、合流点から親へも線を引く。線は一つの太さで、中心どうしで交わるので、合流点を通る線はまっすぐ続く。Mux は、選ばれたモードの 1 から数えた位置か、どのモードも成り立たないことを示す。ブリッジは要求するレーン数を示す。親が `unknown` のソケットは、ルートとは別にまとめて描く。コントローラは描かない。

ソケットは、ID、装着したデバイス、Gbps の一つの目盛りに乗る 2 本のバーを示す。上がデバイスの求めるもの、下がソケットの出せるものである。各バーはレーン 1 本を 1 ブロックとし、ブロックの幅をその世代のレーン 1 本の速度にする。これで、2 本のバーはレーン数と世代の両方を比べる。目盛りはボードごとに決め、どのボードでも、そのボードでいちばん長いソケットのバーを一定の幅で描く。上のバーのうち下を超えた部分は不足として印を付け、下のバーのうち上を超えた部分は薄く描く。空のソケットは出せるものだけを示し、何も出さないソケットはバーを示さない。Mux が無効にしたソケットは、取り消し線を付けて描く。

ルートは、レーン数で数える 2 本のバーを示す。各ブロックがレーン 1 本である。上が子の要求するレーン数、下が供給するレーン数である。そのボードでいちばん長いルートのバーも、同じ一定の幅で描く。供給を超えた要求には、超過として印を付ける。

ソケットのものもルートのものも、64 本より多いレーンのバーは、レーン 1 本ごとのブロックでなく、多くて 2 つのブロックで描く。印の付き始める所までのレーンと、その先のレーンである。長さと印は、レーン 1 本ごとに描いたバーと同じにする。

### レポート

レポートの状態、各診断の重大度・メッセージ・コード、評価したデバイスそれぞれのリンクを示す。

### 見た目

#### 配置

ボード、パーツ、rig の一覧は左のサイドバーに並べ、レポートは右のサイドバーに置き、トーナメント表はその間に置く。ヘッダーの色がウィンドウを囲む枠になり、トーナメント表と、二つのサイドバーの各一覧は、それぞれその枠にはめ込んだ角の丸みの小さいくぼみの中にある。サイドバーのくぼみは、サイドバーとトーナメント表の間と同じすき間をあけて縦に並ぶ。トーナメント表はヘッダーの下の高さいっぱいを占め、各サイドバーはそのくぼみと下端の操作とを合わせて同じ高さを占める。各くぼみはその中でスクロールするので、ページはスクロールせず、ヘッダーとほかのくぼみは動かない。

#### サイドバー

サイドバーの内側の縁をドラッグするか矢印キーで動かすと、サイドバーの幅が 180 から 480 ピクセルの間で変わり、その幅をブラウザに記憶する。縁をダブルクリックすると、初めの幅に戻る。

左のサイドバーのボード、パーツ、rig の各一覧は、その見出しで見出しだけに畳み、また開く。開いている一覧でサイドバーの高さを分け合い、どれが開いているかをブラウザに記憶する。見出しの横にあるファイルを作る操作では、一覧は畳まれも開かれもしない。

どちらのサイドバーでも、二つのくぼみの間のすき間をドラッグするか矢印キーで動かすと、その上と下の開いている一覧の間で高さが移り、どの一覧も 80 ピクセルより低くはならない。その高さをブラウザに記憶する。畳んだ一覧の高さは、開いている一覧にその高さの比で分ける。すき間をダブルクリックすると、初めの高さに戻る。狭い画面では、すき間は動かない。

サイドバーの各見出しは、トーナメント表から遠い側の端にその一覧のアイコンを示す。各サイドバーは、くぼみの下にくぼみと同じ幅で横に伸びる下端の操作で、細い列に畳む。この列では、各くぼみがそのアイコンだけに縮んで上から並び、下端の操作は残った高さいっぱいに伸びる。列のアイコンか下端の操作で開き直す。それぞれが開いているかどうかをブラウザに記憶する。

畳んだサイドバーにポインターを置いている間は、そのサイドバーがその幅でトーナメント表の上に重なって開き、トーナメント表は動かず、くぼみの間のすき間から、サイドバーの外側の端からトーナメント表の側へ薄れていく背景越しに見える。ポインターが離れると、また畳む。開くときは、アイコンをその場に置いたまま幅が広がり、見出しの残りがその横に現れ、広がりきってから一覧が見出しの下に開く。畳むときは、先に一覧を閉じてから幅が狭まる。一覧が開いたり閉じたりする間、下端の操作は一番下のくぼみからくぼみ同士のすき間だけ下にあり、一覧と一緒に縮んだり伸びたりする。下端の操作で畳んだばかりのサイドバーは、ポインターがいったん離れるまで畳んだままにする。

#### 狭い画面

狭い画面では、この三つをこの順に縦に重ねてページごとスクロールし、畳んだサイドバーはアイコンを横一列に並べ、ヘッダーの操作はアイコンだけで示す。

#### ヘッダーと設定

ブラウザのタブのアイコンは、四辺にピンを持ち、角に白い点を置いた緑のチップである。

ヘッダーの操作はアイコンで示し、それぞれの名前をツールチップに出す。操作は、ファイルの読み込み、GitHub からのファイルの読み込み、rig を空にすること、rig の書き出し、ライトとダークのテーマの切り替え、設定を開く歯車である。

設定では、テーマ（システムのライトかダーク、ライト、ダークのいずれか）と、ヘッダーの操作の名前をアイコンの横に出すかどうかを選ぶ。どちらもブラウザに記憶する。テーマを切り替えるか選ぶと、新しいテーマがその操作から広がる円の中に現れる。システムが動きを減らすよう求めているときは、すぐに切り替える。ページは最初の描画からそのテーマで描き、モジュールを読み込む間もサイドバーとトーナメント表の位置を保つ。これで、ページを読み込むときに別のテーマが一瞬見えることも、配置が組み変わることもない。ページは横にスクロールしない。スクロールが要る部分は、テーマの色の細いスクロールバーを持ち、ポインタがその部分にある間だけそれを見せる。

## ビルド

Wasm モジュールは、`mblint-wasm` を `wasm32-unknown-unknown` 向けにビルドし、`wasm-bindgen` コマンドラインで TypeScript の宣言付きの ES モジュールにしたものである。コマンドラインは、`Cargo.lock` にある `wasm-bindgen` クレートと同じ版でなければならない。

ページは、`web/dist` の静的アセットを配る Cloudflare Worker として mblint.shortarrow.jp に公開する。設定は `web/wrangler.jsonc` にある。Cloudflare Workers Builds は `main` を公開し、ほかのブランチを preview としてビルドする。そのとき `web/scripts/cloudflare-build.sh` を実行し、ページをビルドする前に Rust と `wasm-bindgen` コマンドラインを入れる。

Storybook は、`web/storybook-static` の静的アセットを配る二つ目の Cloudflare Worker として storybook.mblint.shortarrow.jp に、誰でも見られる形で公開する。設定は `web/wrangler.storybook.jsonc` にある。その Workers Builds のプロジェクトは `main` を公開し、ほかのブランチを preview としてビルドする。そのとき `web/scripts/cloudflare-build.sh build-storybook` を実行する。Storybook のページはスクリプトを直接書いているので、その応答には Content Security Policy を付けない。ページとは別のオリジンなので、ページの保存した値は読めない。

すべての応答に、`web/public/_headers` にある Content Security Policy を付ける。スクリプトと Wasm はページと同じオリジンのものだけを動かすので、`index.html` にはスクリプトを直接書かない。スタイルはページと Google Fonts から、フォントは Google Fonts から読み、通信はページ、GitHub の API、その生のファイルの置き場にだけ行い、ほかのサイトがページを枠の中に表示することを許さない。

エディタが勧めるキーと列挙された値は、ボード、デバイス、rig のコアの Rust の型から生成し、コミットされたものが生成したものと異なるとき、CI は失敗する。

レポート、カタログ、レイアウトの TypeScript の型は、コアの Rust の型から ts-rs で、型ごとに一つのファイルとして `web/src/report/` に生成する。`cargo test -p mblint-core --features ts` がこれを書き出し、そこにコミットされたファイルが書き出したものと異なるとき、CI は失敗する。各パスの診断の型は、パスの名前を冠して `PhysicalDiagnostic`、`LanesDiagnostic`、`TunnelsDiagnostic`、`ThroughputDiagnostic` と呼ぶ。
