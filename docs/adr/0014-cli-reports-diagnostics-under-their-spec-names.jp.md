# ADR-0014: CLI は、コアで組み立てたレポートから、各診断を仕様上の名前で報告する

[English](0014-cli-reports-diagnostics-under-their-spec-names.md)

- 状態: 採用

## 文脈

PRD は、人向けの出力と、AI エージェントやスクリプト向けの `--json` 出力を持つ `mblint check <rig.toml>` を求めている。その JSON の例は、診断を `BANDWIDTH_TUNNELING_BOTTLENECK` や `VFIO_IOMMU_GROUP_SHARED` と名づけ、すべてを `warnings` の下に置き、添えられた rig からは出てこない値を持つ。PCIe 4.0 x16 のカードに `theoretical_max_gbps = 64.0` とあり、rig が空けている `PCI_E2` が IOMMU グループを共有しているとある。パスはすでに、`Bottleneck` や `SharedIommuGroup` のように診断に名前をつけている。rig、ボード、デバイスのファイルは、データルートからの相対パスで互いを指し、`load_rig` はそのパスを受け取る読み込み関数を通してファイルを読む。PRD は、同じ入力がどの OS でも Wasm でも同じ結果になることも求めており、後の Web ビルドは Wasm で動く。

## 決定

- 最初の CLI コマンドは `mblint check [--data-root <dir>] [--json] <rig>` とする。rig のパスはデータルートからの相対パスで、データルートは `--data-root` で指定しなければ現在のディレクトリとする。
- `mblint-core` は評価結果を、シリアライズできるレポートに変換する。レポートは、状態、各パスの実行状況、パス・重大度・コード・メッセージを持つ各診断、評価したリンクから成る。CLI はそのレポートを JSON かテキストで出力する。
- 診断の `code` は、仕様上の名前を大文字のスネークケースにしたものとする。
- 終了ステータスは、エラーが無ければ 0、エラーがあれば 1、引数かファイルが使えなければ 2 とする。
- テキストの書式とメッセージの文言は、出力の取り決めに含めない。
- PRD の JSON の例を、PRD 自身の rig のレポートに置き換える。これにより、例の値がカードのリンクとも rig とも合わないという未決事項が解決する。

## 理由

- 仕様、コード、出力で名前を 1 組にそろえれば、JSON を読む人は、対応表なしに各診断の意味を `passes.md` で引ける。
- コアで組み立てたレポートは CLI と Wasm ビルドで同じなので、決定性の要件は、2 つのエンコーダーを合わせ続けることではなく、構造によって満たされる。
- データルートからの相対パスは、すべてのファイルがすでに使っているものなので、CLI はテストと同じ方法でファイルを読み、データルートを探す規則を増やさない。
- 終了ステータス 1 をエラーだけに使えば、スクリプトは動かない構成でビルドを失敗させられ、動くが遅い構成を表す警告は通せる。
- テキストと文言を未規定にしておけば、コードとフィールドを読むスクリプトを壊さずに改善できる。

## 採らなかった案

- `BANDWIDTH_TUNNELING_BOTTLENECK` のような PRD のコード: ボトルネックの原因はトンネルの上限、Mux による分割、遅いソケットのいずれでもありうるが、パスは原因を特定しない。それに、1 つ目の語彙と合わせ続ける 2 つ目の語彙が必要になる。
- `errors` と `warnings` を別の配列にする: 重大度は診断のフィールドであり、1 つのリストならパスの順序を保てる。
- `rigs/` の親のように、rig のファイルの位置からデータルートを見つける: 暗黙の規則が増え、`rigs/` の外にある rig では結局フラグが要る。
- CLI だけでシリアライズする: Wasm ビルドが、同じレポートのエンコーダーを別に持つことになる。
- JSON の帯域の値を丸める: 値を比べる側が、パスの持つ精度を失う。
